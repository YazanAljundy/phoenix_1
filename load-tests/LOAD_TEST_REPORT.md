# Phoenix — Full-System Load & Stress Test Report

**Date:** 2026-08-28
**Target:** local backend (`http://localhost:5000/api`), local MongoDB 7.0.34
**Tooling:** k6 v2.2.0 (HTTP), Node + `socket.io-client` 4.8.3 (realtime), custom in-process probe (event loop / pool / CPU profile)
**Production code changed:** none. The backend was exercised only through its public API; the only addition was an instrumentation module loaded with `node -r`, which the application never references.

Every number below comes from a file in `load-tests/results/`. Tables are generated by `node load-tests/build-report-data.js`, not typed by hand.

---

## Executive summary

The system's limit is **single-threaded Node.js CPU**, and it is reached far earlier than expected. MongoDB, the connection pool, the network, Socket.IO and the load generator were all measured and none of them is the constraint — at the failure point MongoDB used **0% CPU** with an empty queue while five of the machine's eight cores sat idle.

Capacity depends heavily on catalog size, so it is reported as two configurations:

| | A — mixed catalogs (200/1k/5k products) | B — realistic catalog (200 products) |
| :--- | ---: | ---: |
| **Maximum observed capacity** | 25 VUs · 23.0 RPS | 100 VUs · 57.0 RPS |
| **Safe operating capacity** | **5 VUs · 11.4 RPS** | **50 VUs · 73.5 RPS** |
| **Breaking point** | **~18 VUs** (15 DEGRADED → 20 FAIL) | **~90 VUs** (85 DEGRADED → 100 FAIL) |
| Throughput ceiling | ~23 RPS | **~77 RPS** |
| CPU cost per request | 52.7 ms | 15.3 ms |

- **Overall error rate:** 0.00 % at every passing level. Across the entire campaign there were **zero 5xx responses and zero timeouts**. The only errors ever produced were HTTP 429 from the rate limiter in the deliberate single-IP control run.
- **Worst endpoints:** `GET /warehouses/:id/products?search=` and `GET /warehouses/:id/manufacturers` — both linear in the size of the warehouse's catalog.
- **Main bottleneck:** Mongoose document hydration. A CPU profile taken under load attributes **~55 % of backend CPU to `mongoose/lib/document.js` and friends**, plus **12.9 % to BSON deserialization** — about 68 % of all CPU spent turning MongoDB documents into model objects, with only **1.5 % idle**.
- **Second bottleneck:** two endpoints that read and hydrate a warehouse's *entire* product collection on every call, regardless of how few rows they return.

A separate, non-capacity finding that matters more operationally: **the deployed rate limiter makes the app unusable for any group of users sharing an egress IP.** See [Rate limiting](#rate-limiting).

### Measurement caveats

1. **The load generator shares the machine with the system under test.** This is quantified rather than assumed: k6 never exceeded **1.5 % of total machine CPU**, and machine-wide CPU stayed at 26–43 % even at failure. The backend was CPU-bound on *one core* while the machine had capacity to spare, so co-location did not cause the observed limit.
2. **Windows timer granularity floors the event-loop metric at ~15.7 ms.** That is the measured idle baseline; lag figures should be read relative to it (e.g. 46.5 ms mean ≈ 31 ms of real lag).
3. `NODE_ENV=development`, so `morgan('dev')` logs every request. That is the configuration this machine actually runs; it was not altered, and its cost is included in every number.
4. This is a laptop-class ULV CPU. Absolute RPS on production hardware will be higher. **The shape of the curves, the CPU attribution, and the algorithmic findings are hardware-independent.**

## Test scenarios

Weighted per iteration so every load level runs the same distribution. `GET /auth/me` runs on every iteration, matching the Flutter app's launch/resume behaviour. Think time is 1–3 s, so a VU models a person, not a closed loop.

| Share | Scenario | What it does |
| ---: | :--- | :--- |
| 40 % | **B** Browsing | banners → exchange rate → warehouses → profile → manufacturers → categories → products → page 2 |
| 15 % | **B** Search | `products?search=` |
| 7 % | **B** Manufacturer filter | `products?manufacturer=` |
| 15 % | **D** Order history | order list → one detail → returnable orders |
| 5 % | **D** Order detail | detail read in isolation |
| 8 % | **C** Shopping | three catalog pages, then `POST /orders` |
| 4 % | **E** Returns | returnable orders + return list (reads) |
| 3 % | **F** Reviews | read reviews → `POST /reviews` → re-read |
| 2 % | **A** Authentication | `POST /auth/login-password` → `/auth/me` → warehouses → manufacturers |
| 1 % | Warehouse panel | pharmacist warehouse detail + `GET /warehouse/orders` |

Measured separately, because each is a different kind of number:

- **G Notifications** — `POST /admin/notifications` fan-out, with concurrent read traffic to measure collateral damage.
- **H Socket.IO** — connection capacity, event fan-out, reconnection storm.
- **Uploads** — `POST /returns` (Cloudinary), at low concurrency by design.
- **Catalog scaling** — every read endpoint at concurrency 1 against 200 / 1,000 / 5,000-product catalogs.

**Scenario C note:** Phoenix has no cart API. `lib/features/cart` holds the basket in client state and submits it as `items` on `POST /orders`, so "add to cart", "change quantity" and "remove item" generate no server traffic and cannot be load-tested as endpoints. The scenario models what the server actually sees: repeated catalog reads, then one order write. See `LOAD_TEST_GAPS.md`.

### Rate limiting

`app.js` sets `trust proxy: 1`, so `express-rate-limit` keys its buckets on `X-Forwarded-For` rather than the socket address. This was verified empirically before relying on it: two requests with different `X-Forwarded-For` values each received `RateLimit-Remaining: 299`, while a repeat of the first decremented to 298.

Every request in the main suite therefore carries a distinct simulated client IP from a bounded pool of 60,000 — modelling real users, who arrive from many addresses, instead of a load generator, which arrives from one. Without it the only measurable quantity is the limiter.

The control run leaves that off and is reported alongside.

## Catalog-size scaling

Concurrency 1, 15 samples after 3 warm-ups — so this measures cost as a function of *data*, independent of load.

| Endpoint | 200 products | 1,000 | 5,000 | pre-existing (344, catalog-linked) | Growth |
| :--- | ---: | ---: | ---: | ---: | ---: |
| `products?limit=20` (cursor page) | 20 ms | 19 ms | 22 ms | 19 ms | **×1.08** |
| `warehouse_profile` | 16 ms | 9 ms | 9 ms | 11 ms | ×0.61 |
| `products?manufacturer=` | 44 ms | 43 ms | 47 ms | 85 ms | ×1.05 |
| `products?search=Medicine` | 39 ms | 131 ms | **624 ms** | 63 ms | **×16.2** |
| `products?search=` (matches **1** product) | 31 ms | 111 ms | **537 ms** | 65 ms | **×17.2** |
| `warehouse_manufacturers` | 28 ms | 111 ms | **554 ms** | 74 ms | **×19.9** |

Data grew 25×; those three endpoints grew 16–20×. The decisive row is the narrow search: it **matches exactly one product and returns an empty-to-1-row payload, yet costs 537 ms**. The cost has nothing to do with the result — it is proportional to the catalog.

The code says why:

- `listDistinctManufacturersForWarehouse` runs `Product.find({ warehouseId, isActive: true }).populate('masterProductId')` — the whole catalog — then reduces it to a `Set` of ~10 manufacturer strings. Nothing is cached.
- `listWarehouseProducts` with a `search` term runs `Product.find(baseFilter).populate('masterProductId')` — again the whole catalog — then filters in memory with a regex, because a catalog-linked product's name lives on the populated `ProductCatalog`, not on the `Product`, and Mongo cannot match it directly.

At 5,000 products, one search costs roughly **0.11 ms of CPU per product in the catalog**. A 20,000-SKU wholesaler would pay ~2.2 s per search — at concurrency 1.

By contrast the cursor-paginated list is genuinely index-backed and flat, which shows the pattern is fixable rather than inherent.

| Queries in window | 24,052 in 58.2 s = **413 q/s** | — |

**Queries per HTTP request: ~7.2.** That is the real database finding — not latency, but volume. Every authenticated request pays a minimum fixed cost before any business logic runs:

1. `authenticate` → `User.findById` (every request, no caching)
2. `isWarehouseAvailable` → `Warehouse.findOne` **+** `User.findOne` (every product/profile/manufacturer request)
3. the controller's own `Pharmacy.findOne({ userId })` (every order/return/review request)
4. then the actual query, plus `populate`, plus `Offer.find`, plus the manufacturer-discount lookup

Individually each is indexed and fast. Collectively they are 7 round trips whose *results* must then be hydrated into Mongoose documents — which is where the CPU goes.

### Index observations

Reported for completeness; none of them caused a measured problem at this data size, and **none were changed**.

- `users` has no index on `role` or `status`. `listAvailableWarehouses` runs `User.find({ role:'warehouse', status:'active' })` on every `GET /warehouses` — a collection scan. At 537 users it is invisible; it grows linearly with the user table.
- `orders` indexes `pharmacyId` but the list sorts by `orderNumber` descending. A compound `{ pharmacyId: 1, orderNumber: -1 }` would let the sort be index-backed; today it sorts in memory per request.
- The single-document `counters` upsert (`nextOrderNumber`) serialises every order creation. It did not bind at 1.1 orders/s, but it is the natural next constraint on write throughput.
- `products` has a text index that is never used — the search path is an in-memory regex.

Measured separately from HTTP, as required.

| 500 | 500 | **100 %** | 1,619 ms | 1,371 ms | 1,440 ms | 1,548 ms |

All recovered, but the p95 of 1,440 ms has a specific cause the probe caught: **max pending connection-pool check-outs hit 417 against a pool of 100.** 500 simultaneous handshakes need ~1,000 database operations at once, so they queue on the driver pool. No check-out *failed*, so the pool absorbed it — but this is the one place in the whole campaign where the connection pool was visibly under pressure, and it would scale with the size of the dashboard population.

## Notification performance (Scenario G)

Two findings had to be established before this could even be run, and both matter:

1. **There is no notification read API.** `Notification` documents are written on every order-status change and every broadcast, and `notification.model.js` carries a `{ userId, isRead }` index that only a list query would use — but no route exposes them, and the Flutter `Endpoints` class has no entry for one. The data is currently write-only.
2. **FCM delivery is out of scope, correctly.** The test asserts that *no* user has a registered device token and refuses to run otherwise, so a load test can never push to a real device. Actual delivery is Firebase's to measure and needs a separate device/integration test.

What Phoenix owns is the fan-out. Broadcasting to **535 recipients**, three runs:

| Run | HTTP time | Notifications written | Writes/s | ms per recipient |
| ---: | ---: | ---: | ---: | ---: |
| 1 | 1,291 ms | 535 | 414.4 | 2.41 |
| 2 | 1,433 ms | 535 | 373.3 | 2.68 |
| 3 | 1,072 ms | 535 | 499.1 | 2.00 |

The important measurement is what it did to everything else. A steady background caller polling `GET /exchange-rate` — one `findById` — throughout:

| Window | median | p95 | max |
| :--- | ---: | ---: | ---: |
| Before broadcasts | **13 ms** | 21 ms | 31 ms |
| **During broadcast 1** | **1,101 ms** | — | 1,102 ms |
| **During broadcast 2** | **1,242 ms** | — | 1,243 ms |
| **During broadcast 3** | **962 ms** | — | 962 ms |
| After broadcasts | 12 ms | 24 ms | 41 ms |

**Unrelated traffic slowed by roughly 90× for the duration of the broadcast**, then recovered completely.

The cause is in `notification.service.js`:

```js
async function sendToAll(userIds, payload) {
  await Promise.all(userIds.map((userId) => sendToUser(userId, payload)));
}
```

No concurrency limit. Each `sendToUser` is a `User.findById` plus a `Notification.create`, plus six `console.log` calls. At 535 users that is ~1,070 database operations issued simultaneously against a 100-connection pool, and ~3,200 log writes.

At the measured 2.0–2.7 ms per recipient this scales linearly: **10,000 users ≈ 20–27 seconds** of ~1-second latency for every other request in flight; 50,000 users ≈ 2 minutes. The endpoint is admin-triggered, so this is a self-inflicted outage waiting for the first large broadcast.

## Return-photo upload performance (Cloudinary)

Deliberately small — this endpoint spends real quota on a third-party account. 104 uploads total, each a valid 122 KB PNG; every return created was deleted afterwards (which is also what removes the Cloudinary assets). All 104 deletions succeeded.

| Concurrency | Uploads | Uploads/s | med | p95 | max | Failed | Backend CPU |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 1 | 8 | 0.79 | 1,106 ms | 2,368 ms | 2,368 ms | 0 | 3.9 % of 1 core |
| 4 | 32 | 2.12 | 1,579 ms | 2,203 ms | 2,390 ms | 0 | 8.6 % of 1 core |
| 8 | 64 | 4.00 | 1,608 ms | 2,115 ms | 2,486 ms | 0 | 15.0 % of 1 core |

Baseline for attribution: `POST /orders` from the same account — the same auth, pharmacy-lookup, validation and Mongo-write path with no upload — has a median of **24 ms**.

So of the ~1,106 ms median upload, roughly **1,080 ms is the Cloudinary round trip**. This is I/O-bound, not CPU-bound: throughput scales almost linearly with concurrency (0.79 → 2.12 → 4.00 per second) while backend CPU stays low and event-loop lag never leaves its idle baseline.

The architectural risk is ordering, not speed. `return.controller.js` uploads every photo **before** validating the return, and deletes them again if validation then fails. A pharmacist submitting a return outside the 48-hour window pays a full Cloudinary upload and delete for a request that was always going to be rejected.

## Login throughput

| Population | Logins | Concurrency | Logins/s | p50 | p95 | max |
| :--- | ---: | ---: | ---: | ---: | ---: | ---: |
| Pharmacy accounts | 500 | 32 | **28.7** | 1,079 ms | 1,211 ms | 2,205 ms |
| Warehouse accounts | 25 | 32 | 23.6 | 645 ms | 963 ms | 1,057 ms |

`bcrypt.hash`/`compare` at cost 10 runs on libuv's thread pool, which defaults to **4 threads**. At ~140 ms per comparison on this CPU that predicts 4 / 0.14 ≈ 28.6 logins/s — matching the measured 28.7 almost exactly.

This is a hard, independent ceiling: it does not improve with more VUs, and raising it means either more thread-pool threads (`UV_THREADPOOL_SIZE`, a config change) or more processes. It is not a problem at steady state — logins are rare per user — but it is a **morning-rush constraint**: 1,000 pharmacists opening the app at 9 a.m. would take ~35 seconds to all get through, with every login taking ~1 s.

## Bottleneck analysis

Walking the stack, with what the measurement showed at each layer:

| Layer | Verdict | Evidence |
| :--- | :--- | :--- |
| Flutter / client | not measured | k6 drives HTTP; client timeouts (15 s) were mirrored |
| Load generator | **not a factor** | k6 ≤ 1.5 % of machine CPU at every level |
| Network | **not a factor** | loopback; 0 timeouts, 0 connection errors in the entire campaign |
| **Node.js / Express** | **BOTTLENECK** | 119–123 % of one core at failure, event-loop lag 3× baseline, 1.5 % idle in the CPU profile |
| Middleware | contributor | `authenticate` adds a `User.findById` to every request; `morgan('dev')` writes a line per request |
| MongoDB | **not the bottleneck** | 0 % CPU, queue 0, tickets never exhausted, cache 26 MB, 0 pool check-out failures |
| Cloudinary | bottleneck **for uploads only** | ~1,080 ms of a 1,106 ms request; I/O-bound and parallelisable |
| Socket.IO | **not the bottleneck** | 3,000 connections at 4.15 % of one core, no ceiling found |
| External services | not a factor | exchange-rate refresh is a daily scheduled job |

### Why Node is saturated: the CPU profile

A 25-second V8 CPU profile taken from inside the process while it was under 25-VU load (`results/profile/cpu-summary.json`), self-time by file:

| Self time | Source |
| ---: | :--- |
| **24.89 %** | `mongoose/lib/document.js` |
| 12.89 % | `bson/lib/bson.cjs` |
| 11.99 % | (native) |
| **10.30 %** | `mongoose/lib/stateMachine.js` |
| **6.16 %** | `mongoose/lib/helpers/document/applyDefaults.js` |
| 3.02 % | `mongoose/lib/query.js` |
| 2.98 % | `mongoose/lib/schema.js` |
| 1.74 % | `mongoose/lib/helpers/populate/getModelsMapForPopulate.js` |
| 1.73 % | `mongoose/lib/model.js` |
| 1.70 % | `mongoose/lib/helpers/document/compile.js` |
| 1.42 % | `mongoose/lib/types/documentArray/index.js` |

Top functions: `deserializeObject` (8.33 %), garbage collector (5.11 %), `Document.init` (4.51 % + 3.74 %), `Document` constructor (4.19 %), `stateMachine._changeState` (4.18 % + 3.50 % + 1.85 %), `applyDefaults` (3.85 % + 1.17 % + 0.94 %), `Document.$__init` (2.51 % + 2.14 %), `$__buildDoc` (2.04 %).

**Idle: 1.5 %.**

Roughly **55 % of all backend CPU is Mongoose turning MongoDB results into model documents**, and another **12.9 % is BSON deserialization** — about two-thirds of the machine's single-threaded budget spent on object construction, not on business logic, not on I/O, and not in the database.

This is what the two problems have in common:

1. **Volume of hydration.** ~7.2 queries per request, every result set hydrated into full Mongoose documents with getters, setters, defaults and change tracking — all discarded moments later by a viewmodel that reads a handful of fields.
2. **Size of hydration.** `/manufacturers` and `products?search=` hydrate an entire warehouse catalog to produce ten strings or one row.

The two compound: at 5,000 products a single `/manufacturers` call constructs 5,000 Mongoose documents, which is why configuration A saturates at one-third the throughput of configuration B.

### Why every endpoint degrades together

Node is single-threaded. One `/manufacturers` call against a 5,000-product catalog occupies the event loop for a few hundred milliseconds of *uninterruptible* CPU. Everything that arrives meanwhile waits — including `GET /exchange-rate`, which needs 8 ms of work and got 942 ms of wall time at p95.

Measured event-loop lag confirms it: 15.7 ms idle baseline → 46.5 ms mean and 1,440 ms maximum at configuration A's 25-VU level. This is head-of-line blocking, and it explains why the failure is broad rather than isolated to the slow endpoints.

### Why throughput collapses rather than plateaus

At configuration B, 75 VUs → 77.2 RPS, but 100 VUs → 57.0 RPS. Beyond saturation, more concurrent requests mean more in-flight Mongoose documents alive at once, more heap pressure, and more GC (already 5.1 % of profiled CPU). GC steals from the same single thread that is the constraint, so added load reduces the useful work rate. Backend RSS sat at 608–630 MB throughout configuration B, with heap up to 252 MB.

## Breaking point

Determined experimentally by bisecting between the last healthy level and the first failing one, per Phase 4.

**Configuration A — mixed catalogs (a third of users on a 5,000-product warehouse):**

```
 5 VUs → PASS       (11.4 RPS, p95 139 ms)   ← verified with a 5-minute soak
 8 VUs → DEGRADED   (13.8 RPS, p95 540 ms)
12 VUs → DEGRADED   (18.8 RPS, p95 686 ms)   ← backend CPU passes 100% of one core
15 VUs → DEGRADED   (18.8 RPS, p95 908 ms)
20 VUs → FAIL       (22.1 RPS, p95 1178 ms)
25 VUs → FAIL       (23.0 RPS, p95 1446 ms)
```

**Breaking point: ~18 concurrent VUs.** Throughput ceiling ~23 RPS.

**Configuration B — realistic 200-product catalog:**

```
 10 VUs → PASS      (19.1 RPS, p95  52 ms)
 25 VUs → PASS      (47.6 RPS, p95  73 ms)
 50 VUs → PASS      (73.5 RPS, p95 394 ms)   ← verified with a 5-minute soak
 60 VUs → DEGRADED  (76.7 RPS, p95 550 ms)
 75 VUs → DEGRADED  (77.2 RPS, p95 757 ms)   ← throughput ceiling
 85 VUs → DEGRADED  (75.2 RPS, p95 983 ms)
100 VUs → FAIL      (57.0 RPS, p95 1233 ms)  ← throughput collapses
```

**Breaking point: ~90 concurrent VUs.** Throughput ceiling ~77 RPS.

Note that degradation is gradual and failure is graceful: no 5xx, no timeouts, no dropped connections, no crash — the system stays correct and gets slow. That is a genuinely good property, and it is why "it didn't crash" was not treated as passing.

## Safe capacity

**Configuration B (a 200-product catalog): 50 concurrent VUs / ~73 RPS**, verified with a 5-minute steady-state soak — p95 394 ms, p99 559 ms, 0.00 % errors, no 5xx, no timeouts, MongoDB idle, pool healthy.

**Configuration A (with a 5,000-product warehouse in the mix): 5 concurrent VUs / ~11 RPS.** The tenfold difference is the cost of the two catalog-linear endpoints.

### Translating VUs to real users

A VU is not an app user. Each VU here sleeps 1–3 s between iterations and issued **1.47 requests/second** at the 50-VU soak. A real pharmacist browsing a catalog generates a request every few seconds while active and nothing at all while not.

At a request every 20 seconds per active user, 73 RPS ≈ **1,400–1,500 concurrently active users**; at a request every 10 seconds, ≈ 700. **These are extrapolations from the measured RPS, not measured user counts** — the honest measured number is the request rate.

Two caveats that dominate any such estimate:

- On a 5,000-SKU catalog the same arithmetic gives ~11 RPS, i.e. roughly 200 active users.
- The 300-requests-per-15-minutes-per-IP limiter is a separate ceiling and, for users sharing an egress IP, a much lower one.

## Testing production

**Production was not tested, deliberately.** The Flutter app defaults to `https://phoenix-1-p2qi.onrender.com/api`; that host was never contacted by this suite, and the seeder refuses any non-local MongoDB target.

If a production or staging test is wanted:

**What must be configured first**
- A staging deployment with its own database — never the production database. Order, review and return scenarios write real business records.
- Dedicated test accounts, approved to `active`, on a reserved phone-number range.
- A staging Cloudinary account, or the upload scenario left disabled.
- `SMS_PROVIDER=console`, so no OTP path can reach a paid provider.
- Known Render instance size and instance count — the results here are for one process on one laptop core.

**Risks**
- Render's proxy terminates and its plans throttle CPU; a small instance will show a lower ceiling than this laptop, not a higher one.
- The rate limiter behaves differently in production: behind Render's proxy, `trust proxy: 1` resolves the client's real IP, so each real user gets their own 300-per-15-minute budget — and users behind a shared carrier NAT share one.
- `POST /admin/notifications` writes one document per active user and degrades everything else for its duration. Do not run it against production.
- Order creation increments a shared `counters` document and is visible to real warehouse dashboards.

**Limits to apply**
- Start at 10 VUs, one level at a time, with a human watching instance metrics.
- Cap at whatever level first shows p95 > 1 s, and stop.
- Reads only on any environment sharing data with real users.
- Keep the per-request client-IP simulation **off** in production — spoofing `X-Forwarded-For` there would both distort the limiter and be indistinguishable from an attack.

**Avoiding impact on real users:** use a separate staging deployment. There is no way to load-test the production instance meaningfully without consuming the same CPU that serves real pharmacists — and since that CPU is the bottleneck, the test *is* the outage.

## Recommendations

Ordered by priority. Every one of these is a **proposal**; no production code was modified.

### P0 — Critical

**P0-1. Use `.lean()` on read paths.**
- *Problem:* ~55 % of backend CPU is Mongoose document hydration, plus 12.9 % BSON deserialization.
- *Evidence:* CPU profile under load (`results/profile/cpu-summary.json`): `document.js` 24.89 %, `stateMachine.js` 10.30 %, `applyDefaults.js` 6.16 %, `bson.cjs` 12.89 %; idle 1.5 %.
- *Expected benefit:* `.lean()` typically cuts read-path CPU by 2–5×. Since the constraint is exactly this CPU, throughput should rise by a similar factor. Highest-value targets: `listWarehouseProducts`, `listDistinctManufacturersForWarehouse`, `listOrdersForPharmacy`, `listAvailableWarehouses`.
- *Fix:* add `.lean()` where documents are read and serialized without being saved. Note `applyResolvedIdentity` currently mutates the document in place — it works identically on a plain object, but each call site needs checking.
- *Production code change required:* **Yes** (service layer).

**P0-2. Stop loading the whole catalog for `/manufacturers`.**
- *Problem:* every call reads and hydrates all of a warehouse's products to return ~10 strings; 554 ms at 5,000 products, at concurrency 1.
- *Evidence:* catalog-scaling table — ×19.9 growth for a 25× data increase, with a 0 KB response.
- *Expected benefit:* 554 ms → a few ms. This endpoint is on the pharmacist's main navigation path and ran at 5.77 RPS in the safe-level mix.
- *Fix:* a `distinct`/`$group` aggregation, or read the existing `warehouse_manufacturers` registry (already indexed `{warehouseId, manufacturerAr}` and already maintained), or cache per warehouse with invalidation on product change. The service comment explains why the registry was not used — that trade-off is worth revisiting now it has a measured price.
- *Production code change required:* **Yes**.

**P0-3. Bound the notification fan-out.**
- *Problem:* `sendToAll` issues an unlimited `Promise.all` over every recipient; ~1,070 simultaneous database operations at 535 users.
- *Evidence:* during a broadcast, `GET /exchange-rate` went from 13 ms median to 962–1,242 ms — ~90× — recovering fully afterwards.
- *Expected benefit:* a concurrency limit of ~20 keeps the broadcast off the critical path. Extrapolated at 10,000 users the current code degrades everything for 20–27 seconds.
- *Fix:* chunk the fan-out with a small concurrency limit, or move it to a background job. Also remove the six `console.log` calls per recipient in `sendToUser` (they are marked `TEMP DIAGNOSTIC`), which cost ~3,200 synchronous writes per broadcast.
- *Production code change required:* **Yes**.

**P0-4. Re-examine the rate limiter.**
- *Problem:* 300 requests / 15 min / IP. One browsing session is ~8 requests. Users behind a shared carrier NAT — normal for mobile in this market — share a single budget.
- *Evidence:* control run at 25 VUs from one IP: **99.24 % error rate, 3,387 × HTTP 429**, 3,413 requests.
- *Expected benefit:* removes an availability cliff that has nothing to do with capacity. It is invisible in single-user testing and total in the field.
- *Fix:* key the limiter on authenticated user id rather than IP for authenticated routes (keep IP keying for `/auth/*`), and/or raise the general limit substantially. Also confirm `trust proxy: 1` matches Render's actual proxy depth — with no normalizing proxy in front, a client-supplied `X-Forwarded-For` becomes the rate-limit key, which is exactly how this suite modelled distinct users.
- *Production code change required:* **Yes** (middleware/config).

### P1 — High

**P1-1. Make product search a database query.**
- *Problem:* search loads the whole catalog and regex-filters in memory; cost is proportional to catalog size, not to matches. A search matching one product costs 537 ms at 5,000 products.
- *Evidence:* catalog-scaling table, `products_search_narrow` row: ×17.2 with a ~0 KB response.
- *Expected benefit:* constant-time search independent of catalog size, and it removes the largest single event-loop stall.
- *Fix:* the underlying cause is that a catalog-linked product's name lives on `ProductCatalog`, so Mongo cannot match it from `Product`. Options: denormalize the resolved name/manufacturer onto `Product` at write time (there is already an unused text index there), or search `ProductCatalog` first and join back. Search is also currently unpaginated.
- *Production code change required:* **Yes** (likely a schema/denormalization decision).

**P1-2. Run more than one Node process.**
- *Problem:* one process uses one core. At failure the machine was 65 % idle.
- *Evidence:* backend at 119–123 % of one core while machine-wide CPU stayed at 26–43 %.
- *Expected benefit:* near-linear throughput scaling with core count. On a 4-core instance, roughly 3–4×.
- *Fix:* `node:cluster` or the platform's own scaling. Two things to check first: the in-memory `express-rate-limit` store becomes per-process (multiplying effective limits by worker count — a shared store would be needed), and `startScheduledRefresh` would otherwise run once per worker.
- *Production code change required:* **Yes** (process model + rate-limit store).

**P1-3. Cache or fold the per-request authorization queries.**
- *Problem:* ~7.2 database round trips per request, several of them fixed overhead — `User.findById` on every request, plus `Warehouse.findOne` + `User.findOne` in `isWarehouseAvailable` on every catalog request, plus `Pharmacy.findOne` in each controller.
- *Evidence:* 413 queries/s at 57 RPS at the failure point, with MongoDB at 0 % CPU — the cost is the hydration, not the query.
- *Expected benefit:* removes 3–4 hydrations per request from the critical path.
- *Fix:* short-TTL cache for user/warehouse status; denormalize `pharmacyId` into the JWT so `Pharmacy.findOne` disappears; `.lean()` + projections where the full document is not needed. Any user-status cache must keep blocked-user revocation prompt — that is the reason the lookup exists.
- *Production code change required:* **Yes**.

### P2 — Medium

**P2-1. Add `{ pharmacyId: 1, orderNumber: -1 }` to `orders`.** The list filters on `pharmacyId` and sorts by `orderNumber` descending; today the sort is in memory. Not yet binding at 8,000 orders, but it grows with history. *Production change: yes (index).*

**P2-2. Add an index on `users` for `{ role: 1, status: 1 }`.** `listAvailableWarehouses` collection-scans `users` on every `GET /warehouses` (5.63 RPS in the safe-level mix). Invisible at 537 users, linear in the user table. *Production change: yes (index).*

**P2-3. Validate returns before uploading photos.** `return.controller.js` streams every photo to Cloudinary, then validates, then deletes them if validation failed. A return submitted outside the 48-hour window costs a full upload plus a delete. Reordering makes the rejection free. *Production change: yes (controller).*

**P2-4. Raise `UV_THREADPOOL_SIZE`.** Login throughput is 28.7/s, matching 4 threads × ~140 ms bcrypt exactly. Raising the pool would relieve a morning-rush login queue. Measure first — it also serves file and DNS work. *Production change: config only, no code.*

**P2-5. Expose the notifications that are already being written.** `Notification` rows accumulate and are indexed for a list query that no route serves; the app cannot show a notification history. This is a product gap surfaced by testing, not a performance issue. *Production change: yes (new endpoint) — a product decision.*

### P3 — Low

**P3-1. Remove the `NOTIFICATION_DEBUG` / `AUTH_DEBUG` / `FIREBASE_DEBUG` logging.** Six synchronous `console.log` calls per notification recipient; marked `TEMP DIAGNOSTIC` in the source. *Production change: yes (trivial).*

**P3-2. Confirm production log format.** This run used `NODE_ENV=development`, so `morgan('dev')` wrote a line per request; production uses `combined`. Worth confirming it writes somewhere non-blocking. *Production change: no.*

**P3-3. Guard the `counters` hot document.** `nextOrderNumber` serialises every order creation through one `findOneAndUpdate`. It did not bind at 1.1 orders/s, but it is the next write-path limit. *Production change: only if write volume grows.*

**P3-4. Drop the unused text index on `products`.** `{nameAr, nameEn, manufacturerAr, manufacturerEn}` as text — the search path is an in-memory regex and never uses it. It costs write throughput and memory for nothing. Revisit together with P1-1, which might make it useful again. *Production change: yes (index).*

## Test-infrastructure defects found and fixed during the campaign

Recorded because they affect how the numbers should be read:

1. **Socket fan-out reported 0 % delivery.** `order.service.js` emits *before* `res.json()`, so the event arrived before the HTTP response was parsed; the driver pre-registered order ids from the response and lost that race every time. Fixed to record arrivals as they land. Re-measured: 100 % delivery at every fan-out width.
2. **Socket listener count reported as 0.** Read after the pool had been closed. Fixed and re-run.
3. **Expected 409s counted as failures.** `POST /reviews` correctly returns 409 once a fixture order has been rated. Reclassified via a k6 `responseCallback`; levels measured before the fix show ≤0.36 % error rates that are entirely this. No level's PASS/DEGRADED/FAIL grade was affected.
4. **`--hold` was ignored for levels in the plan table**, so the first 50-VU soak ran 60 s instead of 300 s. Fixed and re-run at the full 5 minutes.
5. **Per-process CPU sampled as zero.** `Measure-Object` cannot sum `TimeSpan`; projecting `.TotalSeconds` first fixed it.
